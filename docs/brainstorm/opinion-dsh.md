# 意见书 · 产品与叙事设计（dsh）

> 评判标准：用户原话「不是要把几个插件缝合在一起，功能不是越多越好」。

## 1. 拆解参考

| 参考 | 核心机制一句话 | 做得好的一点 | 用户可能不满意的一点 |
|---|---|---|---|
| 格林推演 | 多代理分工读写 8 张世界账本（`refs/shujuku/src/service/simulation/model.ts:90`），再投影成场外信号 | 账本字段被逼到可验证：人物带 `knownFacts`、伏线带 `catalyst` 与 `expiresAtDay`（`model.ts:83-84`） | 现行 6 个代理（`agent/agent-catalog.ts:5-12`）+ SQL 交付，用户看不到它在算什么；一轮成本高 |
| 构画 | 事件线 + 大纲拍 + 潜伏注入（`business/lines/injection.js:3-4`，深度 4 常驻注入） | 线只有 5 个阶段（`business/lines/schema.js:4`），状态机干净 | 日程、日历、小剧场、局外聊天全塞进来，功能面盖过主线 |
| 世界引擎 | 每轮对话后调独立 API 推一份世界状态 JSON 再注入 | 注入有分级与上限（`world-engine-inject.js:89-135`），不是无脑全灌 | 重 roll / swipe / 切聊天时状态对不上（`docs/reroll-decouple-fix.md`）；骰子驱动的区域事件像在替用户掷剧本 |
| 故事神谕 | 方案卡（goal/seed/why）→ 选强度 → 悄悄注入 → 完成/放弃（`index.js:184-194`、`:7807`） | 交互闭环最好：「用户点头才生效、随时可撤」 | 方案是**无根**的——没有账本，`goal` 全靠当场编；它只是大工具箱里一个模式 |
| 缝合怪预设 | 正文前先跑一次导演，一次产出 inner/act/file/scene/dm_story/npc_track/recall 七块（`refs/stitches/preset_dump.txt:576-646`） | 每轮都有「谁在场、谁离场、下一步想做什么」的显式思考 | 每轮多一次重调用；且 `inner`/`act` 直接和正文模型抢笔，正文变成它的执行稿 |

**结论**：值得抄的只有两样——神谕的「用户点头才生效」和格林推演的「字段必须可验证」。其余都是功能堆叠。

## 2. 功能 1 的最小数据模型

**人物**（一条一个在场/场外角色）

| 字段 | 没有它会出什么问题 |
|---|---|
| 名字 + 别名 | 同一人分裂成两条，或两个人被合并 |
| 位置（区域 + 具体地点） | 判不了「他会不会撞上主角」；赶路的人还挂在原地 |
| 当前在做什么 + 预计还要多久 | 人物退化成静态标签，跨轮推演变成「谁都没动」 |
| 知道什么（每条带渠道） | 人人全知，暗线一露头就被所有人看穿 |
| 生死状态 | 死人在下一轮继续出场 |

**暗线 / 伏笔**

| 字段 | 没有它会出什么问题 |
|---|---|
| 一句话事实 + 关联人物 | 暗线无主，无法判断该有反应 |
| 阶段（起线/延展/成形/收束/淡出） | 分不清「已埋」和「已收」，暗线永远悬着 |
| 引信（什么条件让它往前走） | 只能靠「该推进了」硬推，用户能感觉到被安排 |
| 波及面（一人/一圈/一地/一域） | 小事被写成天下大乱 |
| 期限 + 错过后果 | 时间推进没有代价，拖多久都无所谓 |

**世界时间**：`天数 + 时段 + 精度`（精确/约/未知）。只有这三项——没有它，「三天后」和「三小时后」混用，且重 roll 会重复计时；有它但再细分到分钟，没人维护得动。

**明确删掉**：局势刻度（pressure/growth 之类）、传闻传播链、SQL 投影、证据注册表。它们服务于「可审计」，不服务于「用户能看懂」。

## 3. 功能 2 怎么比故事神谕好

- **关系**：推演回答「世界现在怎样」，规划回答「下一步想让世界怎样」。规划**必须读推演账本，不许另起一套**——这是和神谕唯一的本质差别：神谕的 `goal` 是当场编的，我们的方案挂在具体暗线 id 上，卡上直接写「这条暗线在成形期，离收线还差：主角得先知道 X」。
- **发起方式**：用户主动。自动生成规划＝AI 替你决定剧情，而且每轮多一次调用。但可以让推演**打角标**：「有 2 条暗线进入成形期，可以收线了」，用户点了才生成。
- **怎么悄悄影响**：注入的**不是剧本，是既成事实 + 一个由头**。分三档语态（借格林推演的投影分法）：`此地此刻`（下一步就可能撞上）/ `风闻`（有人会顺口提起）/ `暗流`（大势往哪推）。默认只注入 1 条 `暗流`，用户点了「开始引导」才升到 `此地此刻`。绝不注入「你应该让主角……」。

## 4. 功能 3 要不要做：不做

理由：缝合怪一次调用产出 7 个块，等于把正文模型的前置思考搬到另一个模型重做一遍——成本翻倍，且 `inner`/`act` 会和正文抢笔，用户的原话正是指这个。

**若一定要做，唯一可接受的合并方式**：不新增调用，把导演降级为推演的**附加输出**——推演本来每轮跑一次，让它顺手多给 2–3 句「本轮人物动向摘要（给正文模型看）」，随信号一起注入。**绝不单独输出 inner/act/file/scene 全套**。

## 5. 推演提示词必须约束的 7 条

1. **分清来源**：正文＝已发生的事实，世界书＝设定，账本＝上轮结论。三者不许混。
2. **「可能发生」绝不写成「已经发生」**。
3. **认知边界**：读者知道 ≠ 人物知道；扩知情面必须答得出具体渠道（亲历/目击/听闻/书信）。
4. **时间守恒**：只结算正文明确写出的推进；回忆、闪回不重复累加；跨度为零就只结算正文里发生的事。
5. **不替用户行动**：不写主角台词、不决定主角选择、不把主角推进任何场景。
6. **不凭空制造冲突**：没有证据不新增敌对势力或阴谋；冲突只能从已有动机与资源里长出来。
7. **允许「没变化」**：本轮确实没动就交空，不许为了显得有用而编。

## 6. 共同问题

**Q1 MVP 只做 3 件事**：① 人物动向账本（镜头外谁在哪、在做什么、知道什么），每轮更新一次；② 暗线账本（阶段 + 引信 + 期限），可手动增删改；③ 一条「世界侧既成事实」注入（默认 1 条，可关）。

**Q2 明确不做 3 件事**：① 每轮正文前的导演 / inner-act 全套；② SQL 投影与多代理编排；③ 日程、日历、小剧场、局外聊天。

**Q3 每轮最多调用几次**：**1 次**，在「AI 回复完成」后。规划另算，用户点按钮才 +1 次。重 roll / 切 swipe 不重跑（具体见 Codex 的状态一致性方案）。

**Q4 界面最少要什么**：一个侧栏（人物 + 暗线，只读为主）、每楼一个小角标「本轮后台有 N 条变化」点开看、一个「生成下一步方案」按钮。不弹窗、不打断正文。

**Q5 最不同意组长的哪条印象**：两处。① 说格林推演「7 个代理」——现行目录只有 6 个（`agent-catalog.ts:5-12`），另有 9 个已退役（`:16-26`），它自己在往少里砍，这恰恰是「重」的反证。② 说世界引擎「每轮推一份 JSON 再注入」——它其实有分级注入与字数上限（`world-engine-inject.js:89-135`），真正的问题不是注入太多，是注入的东西用户看不懂。
